# Provider adapter authoring

This document is the extension contract for Aculect Mail provider adapters. It
covers the adapter classes already shipped in `src/Providers/Adapters/` and the
additive catalog used to validate future contributions.

## Contract at a glance

An adapter has four declarations that must agree:

1. Its `getSlug()` value.
2. Its registration key in `ProviderAdapterRegistry`.
3. Its `ProviderTypes` metadata, capability map, and bounded credential schema.
4. Its `ProviderAdapterDescriptor`, generated by
   `ProviderAdapterCatalog::fromAdapters()`.

The descriptor binds those declarations to the existing
`ProviderAdapterInterface` without adding a required interface method. This is
intentional: third-party adapters that implement the existing `getSlug()`,
`send()`, and `testConnection()` methods continue to load. The built-in
registry validates the complete catalog at construction and returns no adapter
when the catalog is malformed, duplicated, incomplete, or unregistered.

## Authoring an adapter

1. Add a class under `src/Providers/Adapters/` implementing
   `ProviderAdapterInterface`. Return one stable lowercase slug from
   `getSlug()`.
2. Reuse `AbstractHttpApiAdapter` for JSON APIs. Keep provider-specific URL,
   authentication, request payload, response ID extraction, and provider error
   mapping in the adapter. Reuse the existing SMTP adapter for SMTP-compatible
   behavior where appropriate.
3. Add the slug to `ProviderTypes::all()` and add complete metadata to
   `ProviderTypes::metadata()`. The capability map must contain every key from
   `ProviderTypes::capabilityLabels()` and every value must be boolean.
4. Add the connection credential fields to
   `ProviderTypes::credentialSchema()`. Keep this schema bounded and limited to
   connection credentials. Sender identity (`from`, `from_name`, reply-to, and
   BCC) belongs to the sender-identity settings contract, not the adapter
   credential declaration.
5. Register the adapter under the exact same slug in
   `ProviderAdapterRegistry`. Do not register aliases or duplicate keys.
6. Add a bundled icon entry in `ProviderIcons` using the same icon key exposed
   by the provider metadata. Icons are local SVG fragments; do not add remote
   image hosts or runtime asset downloads.

The catalog is generated from the registry map, so an adapter cannot silently
drift from its canonical metadata or schema. `ProviderAdapterContractValidator`
checks the slug, metadata, capability declarations, required methods,
credential bounds, and normalized result contract.

## Credential and SecretVault boundaries

`ProviderRepository` owns persistence and encrypts sensitive values with
`SecretVault`. An adapter receives a `ProviderConfig` for the current request;
it must not write credentials to options, transients, logs, events, exceptions,
or provider responses. Never print the complete config while debugging. Tests
must use obvious synthetic placeholders and must not contain real tokens.

Credential schema fields use `type`, `required`, `secret`, and `max_length`,
with an optional finite `enum`. The validator caps the field count at 24, each
value at 2,048 characters, enum choices at 32, and each enum value at 64
characters. Secret fields should be marked `secret: true`; this describes the
redaction boundary and does not replace `SecretVault` encryption.

`SecretVault` requires a non-empty WordPress-managed salt or a strong
`AUTH_KEY`/`SECURE_AUTH_KEY` constant before writing credentials. It no longer
derives new keys from a site URL alone. Existing ciphertext created by the
strong-constant path remains readable where those constants are still present;
site-URL-only ciphertext is intentionally unrecoverable and must be replaced
by re-entering the credential after the site has a real WordPress secret.

## HTTP and privacy safety

- Use WordPress HTTP APIs through `AbstractHttpApiAdapter` and a bounded
  timeout. Do not use raw cURL, unbounded retries, or caller-supplied URLs.
- Keep provider endpoints in the adapter and use HTTPS endpoints supplied by
  the provider. Validate region/host choices against a finite enum or a
  bounded, documented value set.
- Send only the fields required by the provider. Do not add message bodies,
  recipient addresses, credentials, or raw provider response context to logs.
- Return `SendResult` for both delivery and connection checks. Use the existing
  `FailureClassifier`/`FailureCategory` mapping for failures and retain only a
  short, sanitized human-readable message.
- `testConnection()` checks provider readiness without sending a message.
  The existing `ProviderTestService` owns an explicit test-send flow and its
  privacy-safe attempt/event records; an adapter must not create its own log
  rows.
- Provider message identifiers may be returned only through the normalized
  `SendResult` field. Do not put provider payloads or headers into that result.

## Internationalization

Provider labels, descriptions, capability labels, and notes are translated in
`ProviderTypes` with the `onesmtp` text domain. New user-visible PHP strings
must follow `docs/developer/i18n.md` and require a regenerated
`languages/onesmtp.pot` (`composer i18n:make-pot`). Developer-only identifiers,
slugs, enum values, and error codes are not translated.

## Testing and release validation

Every adapter contribution should include:

- a registry/catalog test proving the slug, metadata, capability map, schema,
  and bundled icon agree;
- a fixture-backed success, normalized failure, and `testConnection()` test;
- provider request tests with synthetic credentials and no message/address
  assertions beyond the minimum payload shape;
- malformed, duplicate, and unregistered declaration coverage when catalog
  code changes.

Run the PHP and static gates before opening a pull request:

```text
composer lint
composer test
composer analyze
```

If PHP user-facing strings changed, also run `composer i18n:make-pot` and
review the POT diff. Run JavaScript/build or browser checks only when the
adapter change modifies the corresponding assets or visible admin UI. Release
validation must include the repository's normal changed-file checks and must
not introduce provider-specific OAuth, licensing, hosted-service, or schema
changes without a separate decision.
