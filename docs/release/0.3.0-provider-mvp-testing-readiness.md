# OneSMTP 0.3.0 Provider MVP Testing Readiness

Use this checklist to prove the 0.3.0 provider MVP on a staging or local site before any release-facing packaging work. This is a readiness artifact, not a feature claim.

## Scope

- Provider setup, activation, priority, weight, and safe credential entry.
- Provider-specific test send flows and their safe success or failure responses.
- Delivery logging, provider selection context, attempt lineage, and redacted failure details.
- Operational readiness signals for DNS, sender identity, and retry/log visibility.

## Automated And Local Proof

- `tests/Unit/Providers/ProviderTypesTest.php` covers supported provider metadata and capability flags.
- `tests/Unit/Api/RestControllerTest.php` covers provider CRUD validation, safe provider reads, and provider test-send responses.
- `tests/Unit/Admin/ProviderAdminTest.php` covers provider admin state and form behavior.
- `tests/Unit/Admin/LogAdminTest.php` covers log filtering, redaction, resend eligibility, and safe detail views.
- `tests/Integration/Dispatch/CompatibilityMatrixTest.php` covers representative synthetic WordPress email sources against the send pipeline.
- `tests/Integration/Dispatch/LoggingIntegrationTest.php` covers attempt logging, provider context, and lineage output.
- `tests/E2E/Admin/DeliverabilitySmokeTest.php` covers the controlled admin smoke fixture without real credentials or external delivery.
- Local fake proof should use synthetic providers, synthetic recipients, and test doubles only.

## Manual Real-Provider Proof

- Configure OneSMTP on a staging or local WordPress install first.
- Use a disposable inbox or disposable domain for any real-provider check.
- Use a real provider credential only in the staging or local environment under test.
- Send a provider test email from the provider workflow and confirm delivery in the disposable inbox.
- Confirm the provider test response is safe and does not expose secrets, tokens, or provider message IDs.
- Confirm Email Logs show the expected provider, status, attempt number, and redacted error context.
- If the provider requires sender authentication, complete SPF, DKIM, and DMARC prerequisites before retrying the test send.
- If failover is part of the test plan, repeat with a secondary provider and confirm the fallback path is visible in logs.

## Owner Prerequisites

- Disposable inbox or disposable domain.
- Provider credential for the chosen adapter.
- DNS access when sender authentication is required.
- Staging or local WordPress site preferred over production.
- Admin access to OneSMTP settings, provider setup, and email logs.

## Release-Facing Proof Gaps

- `readme.txt` still declares `Stable tag: 0.2.0` and does not yet describe 0.3.0.
- `CHANGELOG.md` still has no 0.3.0 entry under `Unreleased`.
- `package.json` still reports version `0.2.0`.
- No dedicated `docs/release/0.3.0-release-notes.md` exists yet.
- This checklist does not replace release metadata updates; it only records readiness expectations and proof boundaries.

## Pass Criteria

- Automated and local fake proof passes without real provider credentials.
- Manual provider proof is completed on a staging or local site using disposable test data.
- Release-facing metadata gaps are explicitly understood and either accepted for later work or addressed in a separate release-prep change.
